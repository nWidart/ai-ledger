# Design

## Context

See proposal.md for why. The current state (main at e702140, before `feat/web-audit-fixes` merges):

- **Data.** `useApi.ts` is a module-level cache keyed by URL: `values` (the live cache), `inflight` (dedupe), `last` (every URL's last JSON text and object, kept through clears, so an identical answer keeps its object identity), an `epoch` that `clearApiCache()` bumps, and `askedEpoch` so `useLanding` knows whether Refresh or an ingest caused the last clear. `useApi(url, { keepPrevious })` subscribes with `useSyncExternalStore` and returns `{ data, error, loading, retry }`. `getJson(url, init)` is the one `fetch` wrapper; nothing passes a signal. `refresh.ts` polls `/api/status` (60 s, 3 s while ingesting), clears the cache when `last_change` changes (`noteIngest`), orders answers by a `sent`/`shown` counter, and runs Refresh as `POST /api/refresh` then `clearApiCache(true)`.
- **Beside it**, four fetch paths with their own guards: `SessionsDrawer.tsx` (server paging by offset, 200 ms debounce, `seq` ref, refetch in place with `limit: rows.length` when the page payload changes), `cost/drawers.tsx` (`TopSessionsDrawer`, one day's sessions, `seq` ref), `palette/Palette.tsx` (`useApi` for `/api/palette` with keepPrevious and `/api/sessions?q=` behind a 150 ms debounce), `live/useLive.ts` (`getJson` for the list and the selected session, `moved()` guards, a cursor catch-up merged by `mergeSession`, an SSE stream with its own reconnect backoff, a 10 s recheck interval, a status call queue "one at a time, once more", pause and `held`), `errors/marks.ts` (a serial write queue of POSTs that ends with `clearApiCache()`), `errors/Examples.tsx` (`/api/error` full text once per id, kept in a `Map`), `sheets/SessionSheet.tsx` (`/api/prompt`).
- **Routing.** `hash.ts`: the page is the pathname (`/usage`, `/cost`, `/errors`, `/limits`, `/insights`, `/context`, `/live`; the server serves `index.html` for `PAGES` and 302s `/` to `/usage`); the view is the hash (`#project=…&range=…&source=…&auto=1`), plus sheets (`inspect`, `tool`, `mcp`, `skill`, `session`), Errors (`ex`, `cat`, `sub`, `noise`, `gran`, and more in `raw`), Activity (`day`), Live (`view=wall`). `setHash` pushes for `PUSH_KEYS` and replaces otherwise, keeps a `history.state.sheets` depth so `closeSheets` can `history.go(-n)`, drops `VIEW_SCOPED` keys when the view changes, and formats keys in the order the pre-React pages wrote them, so links copied before the React app still open. `go(href)` pushes and scrolls to the top on a page change. `App.tsx` maps the pathname to a page synchronously through `useSyncExternalStore`. The hash is shareable: `>copy link` copies `location.origin + href` with the hash, and the Errors permalinks are `#ex=<id>` and `#cat=<type>` (spec: "Existing permalink").
- **Tables.** `Sort.tsx` is 25 lines: `sortRows(rows, get, desc)` and a `SortTh` header cell; nine files use it. The sessions drawer sorts on the server.
- **Live stream.** `Stream.tsx` draws up to `KEEP = 2000` events (in practice a few hundred rows, as lanes fold and show their last 5), with a Follow placement that uses `scrollHeight`, a `ResizeObserver` and a reach check to tell the user's scroll from the browser's.
- **Build.** One JS chunk: 651 kB minified, 204 kB gzipped; CSS 100 kB / 17 kB. `feat/web-audit-fixes` adds `React.lazy` per page in `App.tsx` and a manual `visibilitychange` pause to the Nav poll and Live.
- **Tests.** 48 Vitest files under jsdom. They stub `fetch` with `vi.stubGlobal` or `mockApi()` (a table of handlers by pathname) and the SSE with `FakeSource`; `test-setup.ts` calls `clearApiCache()` after each test; `Nav.test.tsx` reaches into `fetchCached`/`peekCache`; Live tests use fake timers. Fixtures in `web/src/__fixtures__/` are generated by `tests/test_web_fixtures.py` and type-checked against `api.ts`.

## Goals / Non-Goals

**Goals:**
- One data layer for every GET, with cancellation, eviction, stale-while-revalidate and deduplication the app no longer writes itself.
- Fix the audit items assigned to this change: no `AbortSignal`, unbounded cache and `JSON.stringify` compare, polls in hidden tabs, poll priority. Synchronous page switches moved to `adopt-tanstack-router` (decision 9).
- Every link, bookmark and copied URL keeps working. No server change.
- Each phase ships on its own, passes `npm run check` and can be reverted by itself.
- The bundle grows by Query alone.

**Non-Goals:**
- No change to payloads, URL keys or any figure.
- No router in this change (decision 9). No virtualization. No change to how tables sort.
- No Suspense: the pages' loading states (`useLanding`, the drawers' hints, `aria-busy`) are specified behaviour and stay.

## Decisions

### 1. Query: adopt, as the only data layer

The problems in the proposal are Query's core feature list, and the app already behaves like a Query cache written by hand: `values` is the cache, `inflight` is dedupe, `epoch` is invalidation, `last` is structural sharing's poor cousin, `keepPrevious` is `placeholderData: keepPreviousData`, `retry()` is `refetch()`. At 13 kB gzipped it is the one library here whose weight is clearly repaid: it removes about 300 lines of guard code across six files and the class of bugs they guard against.

**One QueryClient, created in `queryClient.ts`, provided in `main.tsx`.** No module-level singleton is imported elsewhere: everything that needs the client is a hook (`useQueryClient()`), so tests give each render its own client (decision 10). `refresh()` becomes `useRefresh()`; `pollStatus()` becomes a `queryClient.fetchQuery` on the status options from the hooks that need it.

Default options, set once in `queryClient.ts`:

| Option | Value | Why |
|---|---|---|
| `staleTime` | `Infinity` | Data changes only when the store does. Today's cache never expires on its own; invalidation (an ingest with new lines, Refresh, a marks write) is the only trigger, and it stays so. |
| `gcTime` | 5 min (Query's default) | Replaces the unbounded `values` and `last` maps: an answer no view shows for five minutes is dropped. The spec delta says so. |
| `retry` | `false` | The app is on localhost; a failure is "App not reachable" and the page offers Retry at once, as today. Query's default of three retries with backoff would hide the error for about seven seconds. |
| `networkMode` | `"always"` | Query's default `"online"` pauses every fetch while `navigator.onLine` is false. The server is `127.0.0.1`: an offline laptop must still work. |
| `refetchOnWindowFocus` | default (`true`) | With `staleTime: Infinity` it refetches only queries that were invalidated while the tab was hidden; that is how a hidden tab catches up (decisions 5 and 7). |
| `refetchOnReconnect` | `false` | Same reason as `networkMode`. |
| `structuralSharing` | default (`true`) | Decision 3. |

**Query keys.** A `queries.ts` module exports one `queryOptions()` factory per endpoint, so key, URL and type live together and every caller (hooks, `fetchQuery`, `setQueryData`, `invalidateQueries`) uses the same key. Keys are `[resource, ...parts]`, with the `View` object as one part; Query hashes keys deterministically whatever the object's key order, so `{ project, range, automated, source }` needs no stringifying.

| Query | Key | URL | Notes |
|---|---|---|---|
| status | `["status"]` | `/api/status` | Decision 5. |
| usage | `["usage", view, session]` | `usageUrl` | Activity, Cost; `session` is `""` except for the project sheet. `keepPreviousData`. |
| day | `["day", view, day]` | `dayUrl` | Activity's selected day. |
| sessions (one page) | `["sessions", view, opts]` | `sessionsUrl` | Palette search, `TopSessionsDrawer`. |
| sessions (infinite) | `["sessions", "pages", view, { q, near, day, sort, desc }]` | `sessionsUrl` with `offset` | Decision 8. |
| session | `["session", id]` | `sessionUrl` | Session sheet. |
| prompt | `["prompt", id]` | `promptUrl` | Session sheet's whole first prompt. |
| tool | `["tool", kind, name, view]` | `toolUrl` | Tool sheet. |
| palette | `["palette", view]` | `paletteUrl` | `keepPreviousData` (the counts stay while the chosen facet loads, as today). |
| limits | `["limits", { project, range, source }]` | `limitsUrl` | `keepPreviousData`. |
| limits window | `["limits", "window", { provider, limit_id, scope, start }]` | `limitWindowUrl` | History strip. |
| insights | `["insights", view]` | `insightsUrl` | `keepPreviousData`. |
| context | `["context", view]` | the Context page's URL builder (`ContextPage.tsx`, added in #65) | `keepPreviousData`. |
| errors | `["errors"]` | `/api/errors` | Decision 6 for the marks. |
| error detail | `["errors", "detail", id]` | `errorUrl` | "Show full"; `staleTime: Infinity` and never invalidated: a failed call's text does not change. |
| live list | `["live", "list", { project, automated, source }, text]` | `liveUrl` | Decision 7. |
| live session | `["live", "session", id, text]` | `liveSessionUrl` | Decision 7. |

The ingest watcher invalidates `{ predicate: q => q.queryKey[0] !== "status" && q.queryKey[0] !== "live" }`: status is the watcher's own input, and Live is driven by its notices (and the app ingests every second while Live is open, so the watcher would otherwise invalidate every page each minute for nothing new to them; today's behaviour, kept).

**The `useApi` adapter stays as the pages' interface in phase 1.** `useApi<T>(options | null, { keepPrevious })` is rewritten over `useQuery` and keeps returning `{ data, error, loading, retry }`: `data` is `query.data`, `loading` is `query.isFetching || (enabled && query.isPending)`, which is what today's `loading` means (a request for this URL is under way, data may be the previous answer), `error` is `query.error ?? undefined`, `retry` is `query.refetch`. The pages, `useLanding` and their tests change as little as possible in phase 1; the drawers and Live that call `getJson` directly move to queries in phases 2 and 3. The adapter can be inlined later, page by page, when a page is touched for another reason.

**AbortSignal.** `getJson(url, init)` already takes `RequestInit`; each `queryFn` passes `{ signal }` from its context. Query aborts the signal when the query becomes inactive (its last observer leaves: a page switch, a filter change that moves the observer to another key, a closed sheet) and on `cancelQueries`. This is the audit's missing cancellation, for every fetch, with no per-call code. Mutations (`POST`) take no signal: a refresh or a marks write must run to its end.

**`placeholderData: keepPreviousData`** replaces `keepPrevious: true` on usage, insights, context, limits and palette, and `isPlaceholderData` is available to the pages that want to know. The sheets (session, tool, project) keep no previous data, as today.

**Devtools.** `@tanstack/react-query-devtools` is a `devDependency`, loaded in `main.tsx` beside the provider through a dynamic `import()` behind `import.meta.env.DEV`. `main.tsx`, not `App.tsx`: `import.meta.env.DEV` is true under Vitest, so a mount in `App.tsx` would load the devtools (and their Solid runtime) in every test that renders the app. Vite replaces `import.meta.env.DEV` with `false` in a production build and drops the dead `import()`, so the build in `src/ai_ledger/web/` ships none of it and the app's CSP (`connect-src 'self'`) sees nothing new; `tests/test_web_build.py` and an assertion in the close-out task confirm it.

### 2. Query defaults versus today's "clear everything"

Today a clear empties `values`, so a page the user returns to after an ingest shows nothing until its answer arrives (its `last` entry serves identity only). With Query, invalidation marks the query stale and refetches it if active; an inactive query keeps its data and refetches on its next mount, showing the old data meanwhile. That is better and is written into the spec delta ("Back to Activity after an ingest"). `useLanding`'s "quiet swap" rule (new data for the same URL, not asked for, no failure before: no animation) keeps working: `loading` is true while the refetch runs, `data` changes once, and `askedFor()` (below) says whether Refresh asked.

`askedFor(client)` is kept per client in `refresh.ts` (a `WeakMap`, with the watcher's `last_change`), not as a module-level flag, so each test's client starts clean: set when the Refresh mutation succeeds, cleared when the ingest watcher next invalidates. `noteStatus(client, status, asked)` is the one function that takes in a status answer, for the watcher and for Refresh. Its meaning is unchanged: "the data was last invalidated by Refresh rather than by an ingest in the background".

### 3. Structural sharing replaces the stringify compare

`last` exists so that an identical answer keeps its object identity, so a page does not redraw or replay its landing for nothing (spec: "Ingest with nothing new"). Query's structural sharing does the same at the subtree level: after a refetch, every unchanged subtree keeps its reference, and an identical answer is the identical object, so `data !== shown.current.data` in `useLanding` stays false and `useMemo` keyed on `data` stays warm. It walks both trees once on the main thread, as the stringify did, but keeps no text copy of every payload alive. The Errors payload is the largest (every failed call of the store); if a profile shows the walk over it to be noticeable, `structuralSharing: false` on `["errors"]` alone gives up identity for that one query, whose consumers memoize on their own model anyway. Decide from a measurement, not before.

**Measured in phase 2 (task 2.9): keep the default.** The `errors` fixture's rows repeated to the size given, `replaceEqualDeep` (Query's structural sharing) against a parsed copy, median of 15 runs under Vitest on Node 26, Apple M3 Max:

| Failed calls | Payload | Structural sharing | `JSON.stringify` (the old compare) | `JSON.parse` (the fetch itself) |
|---|---|---|---|---|
| 1,000 | 0.16 MB | 0.6 ms | 0.2 ms | 0.4 ms |
| 20,000 | 3.1 MB | 11 ms | 3.4 ms | 6.3 ms |
| 100,000 | 15.4 MB | 54 ms | 20 ms | 32 ms |

The walk costs the same whether the answer is identical or one row changed. It is about three times the old stringify, but it runs once per refetch, and `["errors"]` refetches only after an ingest that stored something or a Refresh: at 20,000 failed calls that is 11 ms, under one frame, at most once a minute. What it buys is worth more than that: an identical answer is the identical object, so the Errors page does not rebuild its model, and after a real change every unchanged row keeps its reference. Revisit `structuralSharing: false` on `["errors"]` if a store passes about 100,000 failed calls, where the walk reaches three frames.

### 4. Refresh is a mutation

`useRefresh()` returns `{ refresh, state }` from one `MutationObserver` per client, shared by the nav and the palette (a `useMutation` per caller would give each its own state, and a failed refresh must keep its text until Retry, which holds because the nav always observes it):

- `mutationFn`: `POST /api/refresh`, answering a `Status`.
- `onMutate`: `cancelQueries(["status"])`, so a poll in flight cannot land after the refresh's answer and show "Ingesting transcripts…" for an ingest that has ended (spec: "Status asked while a refresh runs").
- `onSuccess(s)`: `setQueryData(["status"], s)` (the refresh's answer is the newest status), set `asked`, then `invalidateQueries` with the data predicate of decision 1.
- `onError`: nothing to the cache; the mutation stays in its error state, which the nav shows as "Refresh failed. Select Retry to try again." until the user retries (spec: "Failed refresh waits for Retry"), and the status poll goes on updating the alert and the ingest time underneath, as today.

`RefreshState` (`text`, `failed`, `busy`, `retry`, `alert`) becomes a pure function of the status query's data and the mutation's state, in `refresh.ts`, so the nav and the palette's `>refresh` show the same thing. The `sent`/`shown` ordering goes: Query never has two fetches of `["status"]` in flight, and a refresh's answer is written last by `cancelQueries` then `setQueryData`.

### 5. The status poll is a query with `refetchInterval`

```ts
statusOptions = queryOptions({
  queryKey: ["status"],
  queryFn: ({ signal }) => getJson<Status>(statusUrl, { signal, priority: "low" }),
  staleTime: 0,
  refetchInterval: q => (q.state.data?.ingesting ? 3_000 : 60_000),
  refetchIntervalInBackground: false,
  refetchOnWindowFocus: "always",
})
```

- `refetchIntervalInBackground: false` (Query's default) stops the interval while `document.visibilityState` is hidden; `refetchOnWindowFocus: "always"` asks once when the tab is shown. This replaces the manual `visibilitychange` pause `feat/web-audit-fixes` adds to `Nav.tsx`, which this change removes.
- `priority: "low"` is the Fetch priority hint (`RequestInit.priority`, Chromium and Safari; ignored elsewhere), the audit's "background polls are not low priority". It goes on the status poll and the Live recheck only; a fetch the user is waiting for keeps the default.
- The side effects of a status answer (`setOrder(project_order)`, the ingest watcher) run in the `QueryCache`'s `onSuccess` callback, filtered on `queryKey[0] === "status"`, which is Query's hook for exactly this and runs for every fetch of the key whoever started it: the nav's interval, Live's `fetchQuery`, a focus refetch. The watcher keeps `lastChange` in module scope as `noteIngest` does today and calls `invalidateQueries` when it changes (not on the first answer).
- Live's status request (spec: "at most once at a time, and one more after it for the notices that came meanwhile") is `queryClient.fetchQuery(statusOptions)` with `staleTime: 0`: concurrent calls dedupe onto the in-flight fetch, and the six-line `busy`/`again` loop in `useLive` stays, calling `fetchQuery` instead of `pollStatus`.

### 6. The Errors marks write with `setQueryData`

`useMarks` keeps its serial queue, its `server`/`ops` model and its messages: they are specified behaviour (fix markers, muting, the import, the resync after a failed step) and Query's optimistic-update pattern would only rename them. What changes: each step's POST becomes a mutation (one `useMutation` for fix, mute and import, with the URL and body as its variables: three hooks would differ in nothing else), the resync `GET /api/errors/marks` becomes `fetchQuery(["errors", "marks"])` with `staleTime: 0` so it always asks the store, and the `finally(() => clearApiCache())` becomes `setQueryData(["errors"], d => d && { ...d, fixes: marks.fixes, muted: marks.muted })`: the page's payload carries the marks as the store has them now, with no refetch of the whole Errors payload and no invalidation of every other page, which is what `clearApiCache()` did. Two edges: when a step ends with no marks known (the write and the resync both failed), `["errors"]` alone is invalidated, so a page opened later does not seed from a payload that may lack what the store took; and when an `/api/errors` fetch is under way as a write's answer is cached, the marks are written again once that fetch lands, since its payload carries older marks.

### 7. Live: two always-stale queries, asked by `useLive`; the cursor catch-up lives in the queryFn

As built in phase 4. It differs from the first plan in four places, each for a reason found in the code or the spec: no `enabled` gate, no `refetchInterval`, notices refetch through the observers instead of `invalidateQueries`, and the stream closes in a hidden tab.

- **Two queries.** `queries.liveList(view, text)` and `queries.liveSession(id, text)`, both with `staleTime: 0` and `refetchOnWindowFocus: false`. Query itself fetches only when the page comes to show a key: on mount, another session, another filter, Full text. Every other fetch starts in `useLive` (a notice, a reconnect, the return to the tab, Resume, the recheck).
- **Pause and a hidden tab hold updates by not asking.** There is no `enabled: !paused && visible`. Pause holds updates, not navigation: a paused page still loads a session the user opens, the list for a filter the user changes and the text when Full text turns on, and a gate on `enabled` would have stopped those. `held` is still counted for the label, and Resume asks once however many notices were held. Resume with nothing held sends no Live request, as before.
- **The selected session's catch-up is in its `queryFn`.** It reads the cached value for its own key through the context's `client`, asks for `after = cached.cursor` when there is one and returns `mergeSession(cached, next, true)`; with nothing cached it asks from the start. The `moved()` guards are gone: another session, or another text setting, is another key. `structuralSharing: false` on this query: `mergeSession` already keeps the object of every event it does not replace, and Query's sharing compares arrays by index, so once the oldest events drop off the top at 2,000 it would copy every event and redraw every row.
- **Notices.** A notice asks the list again, and the selected session when it names it or carries `sessions: null`, through the two observers' `refetch({ cancelRefetch: false })`. Each query takes one request at a time and one more after it for the notices that came meanwhile, as the status loop does. No request is cancelled: the app sends a notice a second while Live is open, and with answers slower than that a cancelling refetch would never let one land (found in review of the phase 4 PR). A request found under way was asked before the notice, so one more follows it. The one more is not sent while paused or hidden: Pause counts it as one update held, so Resume fetches; the return to the tab fetches anyway. Not `invalidateQueries`: it cancels, and `refetchQueries` fetches with the options of the query's last fetch, which after a recheck are the low-priority ones. Then the status loop runs (`client.fetchQuery(queries.status)`, one request at a time and one more after it).
- **The recheck** (every 10 s: time-based states need a fetch when no line arrives) is `useLive`'s interval, off while paused or hidden. It calls `client.fetchQuery` with the low-priority variant of the options, for the list and the selected session. Query's `refetchInterval` cannot mark its fetches, and the spec says background polls use low fetch priority while the page's own requests do not. It joins a fetch under way instead of replacing it.
- **Hidden tab.** The stream closes while the tab is hidden and opens again on return, as #74 shipped and `openspec/specs/live-dashboard/spec.md` ("Pause the page's requests while the tab is hidden") specifies: an open stream keeps the app ingesting every second for a page nobody sees. The first plan said the stream stays open; it was written before #74. On return: one fetch of the list and one of the session, and the status loop once; a paused page stays paused and counts one update held. This change therefore adds no `live-dashboard` requirement.
- **Reconnect.** The stream, its backoff and `conn` stay in `useLive`: Query has no transport for server-sent events and the timing is specified to the second. On reopen after a drop the hook asks both queries again and runs the status loop, or counts one update held when paused.
- **What stays on screen.** Turning Full text on keeps the events, and with them the open rows and the scroll, until the text arrives; the list stays while another filter's list loads. Both are kept in state in `useLive`, not as `placeholderData`, which Query drops when the fetch fails: the events and the list also stay when that fetch fails. A list loaded with Full text does not stay once Full text is off: its first-prompt titles must leave the screen.
- **Errors.** `listError` and `sessionError` are the queries' errors, held while the query is asked again (Query clears the error of a query with no data when a fetch starts, which would blink "Session not found" off on every recheck). A 404 on the session still reads as "Session not found" through `ApiError.status`.
- **New for the user.** A session opened again within the cache's five minutes shows its events at once and catches up from its cursor, instead of loading from the start; so does Live opened again from another page. Turning Full text off shows the earlier events without text at once, with the open rows and the scroll kept.
- **`useNow`** (the 1 s tick) is not data and stays.

### 8. Infinite query for the sessions drawer; the Errors "Show more" is not a fetch

`SessionsDrawer` becomes `useInfiniteQuery(sessionPagesOptions(view, { q, near, day, sort, desc }))` with `initialPageParam: 0`, `getNextPageParam: (last, pages) => loaded(pages) < last.total ? loaded(pages) : undefined`, `enabled: open`, and rows as `data.pages.flatMap(p => p.sessions)`. "Show more" is `fetchNextPage()`; `isFetchingNextPage` tells it from a background refetch for the `aria-busy` and the hint; the search box keeps its 200 ms debounce (a `useDebouncedValue` of 6 lines, decision 15), and `keepPreviousData` keeps the rows on screen while a new query loads (the rows go `inert` and `stale` as today while `isPlaceholderData`). When the Activity payload changes after an ingest, the drawer is invalidated with everything else and Query refetches its loaded pages in order, first page first, so the rows refresh in place with focus kept, as today; this is one request per loaded page where today's `limit: rows.length` was one request, acceptable for a drawer that rarely holds more than two or three pages. `maxPages` is not set: a user who paged far wants those rows.

The Errors page's "Show more examples" (`Examples.tsx`, `MSG_PAGE = 30`) slices a list already in the payload; no request is involved, so it is not an infinite query and stays as it is. `TopSessionsDrawer` (one day's sessions, no paging) is a plain `useQuery`. The palette's session search is a plain `useQuery` on `["sessions", view, { q }]` with `enabled: !!q`.

### 9. Router: left to the change `adopt-tanstack-router`

**Superseded on 2026-11-15.** The user asked for this verdict to be reconsidered and then approved a separate OpenSpec change, `adopt-tanstack-router`: TanStack Router owns the URL, the view moves from the hash to validated search params, and old hash links redirect in place. That change does the page transitions, the scroll restoration on Back and issue #69, so this change does none of them and its phase 5 is removed. The comparison below is kept as the reasoning of the first plan; its Transitions and Scroll restoration items describe work this change no longer does.

What Router would give, against what the app has:

- **Typed search params.** Router validates `?search` with a schema and gives typed `Route.useSearch()`. The app's state is in the hash, not the search string, and it is shareable state: `>copy link`, the Errors permalinks, every bookmark. Router's `hash` is a plain string for anchor scrolling (`hashScrollIntoView`), not a parsed state; `createHashHistory` puts the whole path in the hash (`/#/usage?…`), which would break the `/usage` paths the server serves and every existing link. Moving the state to `?search` would need a permanent client-side redirect from every old hash form, would change the URL every user has copied, and would still have to reproduce `setHash`'s semantics: push for some keys and replace for others, the sheet depth for `closeSheets`'s `history.go(-n)`, `VIEW_SCOPED` keys dropped with the view, the canonical key order. `hash.ts` is 150 tested lines that already type the hash (`HashState`).
- **Code splitting.** `React.lazy` per page, which `feat/web-audit-fixes` adds in `App.tsx`, is the same split Router's `createLazyRoute` makes, with seven routes and no loaders.
- **Transitions.** Router's `viewTransition` option wraps the commit in `document.startViewTransition`. `go()` in `hash.ts` can do the same: `startTransition(emit)` so a slow page's render does not block the click, inside `document.startViewTransition?.(…)` when `prefers-reduced-motion` is off, and `App` reads the pathname inside the transition so `useSyncExternalStore` no longer forces a synchronous render (the audit item). About twenty lines.
- **Scroll restoration.** Router caches and restores scroll per location key. Today `go()` scrolls to the top on a page change and Back leaves scroll to the browser, which cannot restore it for content that is not drawn yet. This is a small real gap; if it is wanted, `hash.ts` can keep a `sessionStorage` map from `history.state.key` to `scrollY` in thirty lines. Not in this change; the user wants it as a follow-up change (Resolved Questions).
- **Preloading on hover.** Not applicable: seven pages whose code is one lazy chunk each, and data that depends on the hash.

Cost as first estimated: 30 kB gzipped (measured by `adopt-tanstack-router` at 26.7 kB gzipped), a second source of truth for the URL, and a migration of every link and test. No server change is needed: the server already serves `index.html` for the page paths whatever their query string. First verdict: reject. Current verdict: adopted by `adopt-tanstack-router`, which has its own design.

### 10. Testing

- **A client per test.** `web/src/testing.tsx` exports `makeClient()` (`retry: false`, `gcTime: Infinity`, `networkMode: "always"`, the app's other defaults) and `renderApp(ui)` / `wrap(ui)` that mount `QueryClientProvider` around the component; `test-setup.ts` drops `clearApiCache()`. Query's timers (`gcTime`, `refetchInterval`) run on `setTimeout`, so the Live tests' fake timers cover them; `gcTime: Infinity` in tests avoids a collection firing between awaits.
- **Fetch mocks stay.** The `queryFn`s call `fetch`, so `vi.stubGlobal("fetch", …)` and `mockApi()` work unchanged; MSW would add a dependency to do the same thing. Mocks that count calls will see one fewer in places (dedupe) and must also honour `init.signal` where a test asserts cancellation (`mockApi` grows an `aborted` check).
- **Fixtures** are unchanged: payloads do not change.
- `useApi.test.tsx` is replaced by `queries.test.tsx`: the defaults (`staleTime`, `networkMode`), the adapter's `loading` mapping, invalidation by the watcher, cancellation on key change (the mock sees `signal.aborted`), and `askedFor()`.
- `Nav.test.tsx` stops importing `fetchCached`/`peekCache`; it reads `client.getQueryData(["status"])` or asserts on the DOM.

### 11. Virtual: reject for now

The Live stream draws a few hundred rows at most (`KEEP` is 2000 events, but finished lanes fold and running ones show five rows), of variable height (tool rows expand, lanes nest, prompts and replies carry text). Virtual 3.14 does support bottom-anchored lists (`anchorTo: "end"`, `followOnAppend`, `scrollToEnd`, `isAtEnd`) and dynamic heights (`measureElement`), so the Follow semantics could be rebuilt on it; but `Stream.tsx`'s placement is specified to the row ("Newest event in a lane", "Newest event taller than the stream", the reach check that tells the user's scroll from the browser's) and would have to be rewritten against estimated sizes, and the DOM today is well under the point where that pays. The tables are small (top N) or server-paged at 100 rows. If a profile ever shows the stream or a drawer to be slow, the first step is CSS `content-visibility: auto` with `contain-intrinsic-size` on `.ev` rows and table rows, which costs no bytes and keeps the scroll geometry exact; Virtual is the step after that, and it is incompatible with `content-visibility` on the same rows (both skip rendering, by different means), so one or the other. Verdict: **reject**, revisit on a measurement.

### 12. Table: reject

`Sort.tsx` is 25 lines and the nine tables that use it sort one column with `sortRows`, or on the server. Table v9 (31 kB gzipped, a new `features`/`useTable` API that changed from v8 last month and is marked "fresh") would add column definitions and a row model for the same single-column sort, and the sessions drawer would not use it at all. Verdict: **reject**; revisit if a table gains multi-column sort, column hiding or grouping that the user asks for.

### 13. Form: reject

The app's inputs are filters bound to the hash, two search boxes and checkboxes; there is no form with validation or submission. Verdict: **reject**.

### 14. Store: reject

The three stores (`palette/store.ts`, `refresh.ts`, `theme.ts`) are `useSyncExternalStore` over a module variable, ten lines each, and `refresh.ts`'s state becomes derived from Query in decision 4. Store is alpha (0.11). Verdict: **reject**.

### 15. Pacer: reject for now

Pacer would replace three debounces (the drawer's 200 ms, the palette's 150 ms search and 700 ms settle, `useLanding`'s 150 ms "slow") and could express Live's status loop as an async queue. It is beta (0.24) and 9.6 kB gzipped for what is a six-line `useDebouncedValue` hook in `web/src/components/useDebounced.ts`. Verdict: **reject**, revisit at 1.0 if the app grows more rate-limiting logic (for example a typing-driven server search on every page).

### 16. Hotkeys: reject for now

The palette's `Cmd/Ctrl+K` and the keys inside the dialog are the app's shortcuts. Hotkeys (beta 0.25, 15.8 kB) offers scopes, sequences and user rebinding, none of which the app needs today. Verdict: **reject**; revisit if the user asks for rebindable shortcuts.

### 17. DB, Start, Charts, Redact, the rest: reject

DB (1.0 RC, 108 kB) is a client-side relational store with live queries and optimistic writes for apps that edit their data; this app reads server-computed aggregates and writes two marks. Start is a full-stack framework; the server is Python. Charts would replace the app's own chart code (`components/chart.ts`) wholesale, outside this change's purpose. Redact is a React runtime replacement, not a library to adopt in a React 19 app. Devtools (the shared panel, alpha) is only needed with more than one TanStack library; Query's own devtools suffice.

## Migration phases

Each phase is one PR on its own branch from `main`, started after the phase before it is squash-merged. It passes `cd web && npm run check` and the Python tests, commits the build, and can be reverted alone. `feat/web-audit-fixes` merged as #74 before phase 1, so `main` already has the lazy pages, `usePageVisible.ts` and the manual visibility pauses that phases 2 and 4 remove.

1. **Foundation.** Add the two dependencies at exact versions, `queryClient.ts`, the provider in `main.tsx`, the devtools behind `import.meta.env.DEV`, and `testing.tsx`. No behaviour change; `useApi` still runs. Revert: remove the provider.
2. **Pages on Query.** `queries.ts`, `getJson` with a signal, the `useApi` adapter over `useQuery`, the status query and the ingest watcher, Refresh as a mutation, `askedFor()`; delete the old cache; rewrite the affected tests; spec delta for the hidden tab. This is the phase that fixes the leak, the stringify compare, the missing cancellation and the poll in hidden tabs for every page. Revert: restore `useApi.ts` and `refresh.ts`.
3. **Secondary fetches.** The sessions drawer (infinite query), `TopSessionsDrawer`, the session sheet's prompt, the Errors "Show full", the palette's two queries, the marks mutations with `setQueryData`. Revert per file.
4. **Live.** The list and session queries, notices as invalidation, the cursor catch-up in the queryFn, pause and visibility through `enabled`, removal of the manual visibility pause; spec delta. Revert: restore `useLive.ts`.
5. **Navigation polish.** Removed. `adopt-tanstack-router` replaces `hash.ts`, so `startTransition` and view transitions there would be deleted by it; that change does them and closes issue #69.
6. **Close-out.** README, CHANGELOG, measured bundle sizes, dead code, `openspec validate`, a walk of the app, and the archive of this change. It follows phase 4.

## Risks / Trade-offs

- **Behaviour the tests pin by request count.** Several tests count `fetch` calls or assert the order of answers; Query's dedupe and cancellation change both. Mitigation: phase 2 rewrites those assertions to the DOM state the spec describes, not to call counts, before changing the hooks.
- **`loading` semantics.** Pages and `useLanding` read `loading` as "a request for this URL is under way". The adapter maps it to `isFetching`; a mismatch would show the loading look at the wrong time or skip the landing animation. Mitigation: `queries.test.tsx` pins the mapping for the four cases (first load, refetch after invalidation, key change with placeholder, error).
- **Infinite-query refetch cost.** After an ingest, the drawer refetches each loaded page in sequence instead of one `limit: n` request. Acceptable for the drawer's usual depth; if a user pages far, `maxPages` can cap what is kept. Noted in decision 8.
- **Structural sharing on the Errors payload.** A deep walk over every failed call on each refetch. Measure in phase 2; `structuralSharing: false` on that one key is the fallback (decision 3).
- **`networkMode`.** Forgetting `"always"` would silently stop every fetch on an offline laptop. It is in the defaults and pinned by a test.
- **`feat/web-audit-fixes` conflicts.** Both branches touch `Nav.tsx`, `useLive.ts`, `hash.ts`, `App.tsx`. This change starts after that branch merges and removes its manual visibility pauses in phases 2 and 4; the rest of its work (lazy routes, chart fixes) is kept.
- **Query's own timers under fake timers.** `gcTime` and `refetchInterval` use `setTimeout`; a test that fakes `setTimeout` but not `Date` can see Query's interval fire. Mitigation: `gcTime: Infinity` in the test client, and the Live tests already fake `Date`.
- **`fetch` `priority` typing.** `RequestInit.priority` is in TypeScript's DOM lib; if the installed `lib.dom` lacks it, a one-line type augmentation in `api.ts` carries it.

## Resolved Questions

Answered by the user on 2026-11-15, before implementation started.

- **Refetch on tab return: only the queries invalidated while hidden.** `refetchOnWindowFocus` stays at Query's default for the data queries; only the status query uses `"always"` (decision 5). The status answer on return invalidates the data if an ingest was missed, so the page is at most one request behind.
- **An ingest does not invalidate the Live queries.** The watcher's predicate skips `["live"]` (decision 1). Live follows its own notices, and its reconnect path catches up after a drop (decision 7).
- **Scroll restoration on Back: wanted.** It is now part of `adopt-tanstack-router`, not a follow-up to this change.
- **Rejecting TanStack Router: accepted at first, then reconsidered.** The user approved `adopt-tanstack-router` the same day; decision 9 says what that changes here.
